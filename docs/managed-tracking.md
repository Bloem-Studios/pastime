# Household profiles and native Bloem tracking

How Pastime keeps household profiles and links them to a Bloem Server. Verified-identity linking and sign-in claims are implemented; an administrator activates them with `pastime-bloem-register`.

## Accounts and profiles

An account owns login authority, roles, sessions and verified OIDC identities. A tracking profile owns its library, history, statistics, lists and personal connections. Existing personal records retain their identifiers and move into the account’s default profile during migration.

Browser sessions list authorized active household profiles with `GET /api/v1/profiles`. A personal request can select one with `X-Pastime-Profile-ID`; omitting it selects the account default. The web chooser retains selection across navigation/reload and separates cached requests by profile. Selection does not grant access to another account. Machine tokens stay bound to the profile selected when issued and cannot switch or enumerate the household.

Public list links retain the account username/slug namespace. Slugs are unique across the whole account as well as within each profile, preventing two household lists from sharing a public address.

## Admission and identity

Local registration remains off unless `PUBLIC_REGISTRATION=true`. The public form accepts username, display name, email and password; creation is always member-only and uses the existing password rules and rate limits. Contact email is not ownership proof. Registration does not automatically link an identity from a single sign-on provider.

OIDC auto-creation is separately controlled by `OIDC_AUTO_CREATE`. Native Bloem provisioning uses stable instance/account/profile identifiers and separate monotonic account/profile revisions. It never merges accounts by matching email or names; only a verified issuer and subject link or claim an account.

## Verified identity and sign-in claims

Each instance has an identity issuer: the issuer whose verified identities the Bloem host may send with an account. An operator sets it at registration (`-identity-issuer`) or later (`-set-identity-issuer`). An empty issuer can be set at any time; a non-empty one changes only while no managed account carries an identity and no sign-in issuer is declared.

Provisioning accepts an identity only under the instance's identity issuer, otherwise it returns 403 `bloem_identity_mismatch` (also when the instance has no issuer). A newer account revision may attach an identity, clear it, or move an unclaimed integration-owned account to another identity. Sending an identity that another account of the instance holds returns 409 `bloem_identity_conflict`; a unique index enforces one account per identity and instance. At an equal revision the identity cannot change.

An account handed to a person, by a sign-in claim or by linking a new account to an existing member, is bound to the identity it was handed over under (`bound_issuer`/`bound_subject`). A newer revision may clear its identity, which keeps the claim, the sign-in and tracking, and may bring the bound identity back, but any other identity returns 409 `bloem_identity_conflict`, whether it arrives in one revision or after a clear. So a corrected link in Bloem never moves one person's ongoing tracking into the account another person claimed; it surfaces as a held-back account instead. The plugin reads both codes and holds back only the affected account (snapshot acceptance and acknowledgement wait for it). `-show-identity` counts claimed or linked accounts whose identity Bloem has since cleared, for an operator to review. While any account is bound, the instance identity issuer cannot change.

An administrator undoes a claim with `pastime-bloem-register -revoke-claim -instance ID -source-account ID` (`Store.RevokeClaim`), for example after the Bloem link turns out to name the wrong person. Under the account lock, the managed account row lock and then the user row lock, it removes every way into the Pastime account and every place its activity goes: all single sign-on identities, the password and the authenticator that could reset it, sessions and tokens (new sign-out-everywhere epoch), pending invitations, calendar feeds, the public profile, server webhooks, linked services and their pending authorizations, notification targets, reading-sync keys and Connect Silo keys. Tracked history and profiles stay. The managed account becomes pending, unclaimed, unbound and without an identity; its source fingerprint stays, so a replay of the delivered revision changes nothing and the next newer revision attaches whatever identity Bloem then holds, which that person can claim. Correct the link in Bloem first. It refuses an account that was not claimed (`bloem_account_not_claimed`; a link to an existing member is not undone this way) and an owner or administrator account (`claimed_account_privileged`; change the role first). It records `bloem.account.unclaim` with identifiers and counts, never issuers or subjects.

A new managed account links to an existing Pastime account only when exactly one active member, not yet mapped in the instance, signs in with the same subject under the instance's identity issuer or under a declared sign-in issuer whose subject shape matches. Owners and administrators are never linked. Otherwise the integration creates a pending member account without a password.

Pastime usually signs in through a different provider application than the one that verified the Bloem login. An operator declares that equivalence with `-declare-login-issuer`, which must equal the configured `OIDC_ISSUER`, together with the provider's subject mode: `user_uuid` (canonical lowercase UUID) or `hashed_user_id` (64 lowercase hexadecimal characters). A subject of the wrong shape never claims or links, so two applications that form subjects differently are never treated as equal. Removing the declaration stops new claims; existing claims and sign-ins stay.

When a verified sign-in matches no Pastime sign-in and is not a link request, the callback first tries a claim, in the same transaction and before any automatic account creation. Candidates are accounts in active instances whose identity equals the token's subject under the instance's identity issuer, reached either because the sign-in issuer is that issuer or because it is declared for the instance with a matching subject shape. No candidate falls through to automatic creation or `identity_unlinked` as before. Exactly one candidate is claimed only if the source account is active (`source_inactive`), the integration created it and it is still pending (`not_pending`), the Pastime account is active (`disabled`), a member (`privileged`), has no password (`has_password`) and has no other sign-in (`has_identity`); several candidates are refused as `multiple_matches`. A claim links the sign-in, marks the account linked with `claimed_at`, records `bloem.account.claim` (instance, source account, sign-in issuer and instance issuer, no subject) and then signs in normally, so the person lands in the account that already holds the tracked history of each profile. A refusal returns 403 `identity_claim_conflict`, which the sign-in page shows as "ask your administrator"; the server logs the reason and identifiers only and creates nothing. Email is never compared.

Claims lock the managed account row before the user row, the order provisioning uses, so a claim and a concurrent identity change serialize: whichever commits first wins and the other sees its result. Claims also hold the instance row shared, which serializes them with issuer changes and declarations.

`-alias-login-subject` adds a second subject under an issuer for the account that already signs in with an existing subject and keeps the existing one. Operators use it before a provider switches subject modes so an account keeps its sign-in. It records `oidc.subject_alias` with the issuer and no subjects. `-show-identity` prints counts and issuer URLs only.

## Implemented backend boundary

| Endpoint/service | Current behavior |
| --- | --- |
| `POST /api/v1/integrations/bloem/profiles:provision` | Source-bound member/profile provisioning, revision conflict/replay checks, explicit activity states and lifecycle credential revocation |
| `POST /api/v1/integrations/bloem/profiles/{profileID}/credentials:issue` | Durable issuance replay, encrypted backend credential storage, rotation and profile binding |
| `POST /api/v1/integrations/bloem/credentials:inspect` | Profile-bound credential/source inspection |
| `POST /api/v1/integrations/bloem/events:apply` | Trusted catalog matching and transactional start/pause/stop effects, event/consumption receipts and ordered resume state |
| `POST /api/v1/integrations/bloem/snapshots:page` | Exact replayable page receipts against fully provisioned revisions and fingerprints |
| `POST /api/v1/integrations/bloem/snapshots:complete` | Final-page receipt verification, revision-safe archival and `{"completed":true}` acknowledgement |

Provisioning, issuance and snapshot endpoints require the dedicated backend provisioning bearer credential; inspection and playback require the profile tracking credential. Browser cookies, personal tokens and profile override headers grant no provisioning authority. Credentials must stay in protected backend configuration; no UI key editor or credential display is implemented. Grant registration is an administrator-authorized service with a root-only operator command (`cmd/pastime-bloem-register`), not a public setup endpoint.

Issuing a profile credential under a new issuance ID supersedes the previous one instead of revoking it: the superseded credential keeps working until the host first uses its successor, or for at most 24 hours, so a failed host commit after issuance does not strand the profile. A superseded issuance cannot be reissued. Lifecycle revocation (source disable, deletion or snapshot absence) stays immediate for current and superseded credentials. Source account disable revokes native credentials without disabling an independently linked administrator login. Source deletion/inactivation archives integration-owned additional profiles and preserves history. Reactivation cannot resurrect revoked credentials. Changing an already mapped default source profile currently returns a conflict pending explicit reconciliation.

A provisioning mapping returns `connection_ready=false`; readiness is established only after encrypted source enrollment commits. Playback HTTP ingestion requires trusted external media identifiers before effects. An episode resolves by its TMDB id, else by TMDB's placement of its IMDb or TVDB id, else by its season and episode numbers. Sources number episodes in other orders and may derive ids from those numbers, so an identifier found at other numbers than the event's is accepted only when the optional episode `title` or `air_date` agrees with it and not with the episode at the event's numbers (or the reverse, which selects that episode); otherwise the event is refused as `no_match`. An episode whose title and air date both disagree is refused as well; a differing title alone is not. Air dates a day apart agree. The title and air date never identify media on their own and are ignored for movies. Completed movie/episode history uses the same consumption receipts as live playback. The stable consumption ID alone identifies a viewing, so a later delivery with a different timestamp is an idempotent replay that records no second play. A newer source revision may move an entity to a different catalog target after a metadata correction; the previous target's integration resume point is removed unless another integration entity of the profile still resolves there. One revision naming two targets is still a conflict. Reverse sync, ratings and unwatched edits remain unsupported.

Snapshots expire after ten minutes, accept at most sixteen concurrent snapshots, one hundred profiles per page and one thousand pages per snapshot. Completion requires the final page receipt and the entire accepted cursor chain. It archives absent integration-owned additional profiles only below the accepted revision ceiling, preserving newer mappings, default profiles and independent login authority. An empty snapshot establishes no revision ceiling and does not archive unknown mappings.

## Integration and rollout boundaries

The acceptance tests run a Bloem host and the real plugin against the actual Pastime HTTP API with isolated PostgreSQL schemas and synthetic catalog metadata. They cover one account with three independent profiles, per-profile encrypted credentials, replay and history deduplication, stale resume protection, later-added profiles, rename and deletion, cancellation and reactivation, restart convergence and revoked grants. They show isolated integration behavior, not live provider or catalog correctness or production readiness.

User-managed exclusion remains separate work. Automatic account creation and tracking do not by themselves grant a user login ownership: only a verified sign-in claims or links an account, and email is never proof.

Before enabling managed tracking on a live installation, rehearse a backup and restore and try it with a small group first.

## Calendar artwork and personal additions

Authorized source releases use verified movie or series provider identities to find shared Pastime title metadata. Episodes resolve through their series identifiers. A batch lookup supplies the poster and title link only when exactly one root matches without contradictory IDs. Source release identifiers and subscription UIDs remain unchanged; metadata resolution does not create personal library entries. Unknown or ambiguous identities retain the source event without an invented title link.

Missing metadata is queued through the durable worker using existing configured providers. Each calendar request queues at most fifty distinct missing identities; a daily deduplication key bounds retries. Provider calls run outside the calendar request. The calendar and Home's Coming soon row both project the linked profile's authorized personal release feed automatically. Imported releases require no additional add action and disappear when the source authority expires or the source selection is removed. Posters and wide root artwork resolve through verified title identities; release cards show sharp artwork.

This projection does not silently overwrite independent Pastime library status, progress, notes or history. Native planned tracking records independent watchlist membership transactionally. Personal-state return synchronization remains a separate capability; it stays disabled until bidirectional convergence, additions/removals and conflict handling are verified.

## Native personal state

Movie and series title pages expose independent favourite and watchlist additions and removals. The native personal-state API uses profile-scoped authorization and idempotency receipts; removing membership retains a tombstone and does not delete unrelated progress, notes or history. Managed source events compare their committed time against newer native choices before applying an effect, and stale deliveries still retain receipts and source revision evidence. Rating removals are explicit timestamped tombstones in remote reads, including when the rating is now null. The transport exists independently of activation; source return-sync flags stay disabled until complete engine acceptance passes.
